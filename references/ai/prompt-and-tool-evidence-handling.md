# Prompt and Tool Evidence Handling

> Last reviewed: 2026-04-18 | Next review: 2026-10-18 | Priority: Essential | Audit Level: 3-4 | Automation: Partial (log collection, hashing, normalization, and quarantine pipelines automatable; legal review, disclosure decisions, and final evidence interpretation manual)

Use this guide when prompts, model outputs, tool invocations, approvals, retrieved documents, or browser-agent actions may need to be preserved as **evidence** for incident response, audit, or post-incident review.

This file extends `ai-agent-incident-response.md` by explaining how to collect, classify, normalize, redact, store, and safely analyze AI workflow evidence without destroying context or creating new leaks.

---

## 1. Why evidence handling matters

AI incidents often involve mixed-trust data:

- attacker-controlled prompts or documents,
- model-generated outputs,
- tool parameters and results,
- human approvals and overrides,
- browser state, downloads, or screenshots,
- logs that may contain sensitive customer or employee data.

Teams fail when they either:

- delete too much too early during containment,
- keep only screenshots and lose the real timeline,
- preserve raw evidence without classification or redaction controls,
- replay dangerous tool actions against live systems.

The right goal is **preserve first, normalize second, analyze safely**.

---

## 2. Evidence types

Treat each of these as a distinct evidence object, not one giant transcript.

| Evidence type | Examples | Typical trust level |
|---|---|---|
| Prompt input | user message, imported task, retrieved corpus chunk, web page text | often untrusted |
| Model output | natural-language answer, plan, generated code, tool request | untrusted or mixed |
| Tool invocation | tool name, parameters, caller identity, time | higher-confidence telemetry if generated by platform |
| Tool result | stdout, API response, retrieved file content, browser DOM | untrusted if sourced from external or attacker-controlled systems |
| Approval event | approve / deny action, reviewer identity, timestamp | trusted if platform-generated |
| Policy decision | blocked by rule, downgraded to read-only, approval required | trusted if platform-generated |
| Runtime telemetry | network logs, system event logs, sandbox audit trail | trusted but still contextual |
| Artifact state | git commit, diff, build artifact, uploaded file, screenshot | mixed; depends on source and integrity proof |

Do not assume model output is trustworthy just because your system produced it.

---

## 3. Trust labels for evidence

Use a simple trust scheme while investigating:

| Trust label | Meaning | Examples |
|---|---|---|
| `Trusted telemetry` | platform or control-plane generated record with integrity value | audit log, signed event, immutable object metadata |
| `Operator asserted` | human note or timeline annotation | analyst summary, responder comment |
| `Untrusted content` | attacker-controlled or potentially attacker-influenced data | prompts, retrieved web text, uploaded docs, tool output from external systems |
| `Derived evidence` | normalized, redacted, or enriched version of another item | parsed JSON, extracted indicators, redacted transcript |

Always preserve the parent-child relationship between raw and derived evidence.

---

## 4. Minimum evidence record

Every collected item should carry enough metadata to stand on its own.

| Field | Purpose |
|---|---|
| `evidence_id` | unique identifier |
| `incident_id` | groups related objects |
| `collected_at_utc` | collection timestamp |
| `event_time_utc` | actual event time if different |
| `session_id` | ties to agent session or conversation |
| `actor_type` | user, agent, tool, system, reviewer |
| `actor_id` | identity or service label |
| `source_system` | app, runner, browser session, MCP server, SIEM |
| `evidence_type` | prompt, output, tool_call, approval, artifact, log |
| `trust_label` | trusted telemetry, operator asserted, untrusted content, derived evidence |
| `classification` | internal confidentiality / privacy label |
| `content_hash` | integrity check for the stored blob |
| `parent_evidence_id` | links derived evidence to original |
| `redaction_status` | raw, redacted, tokenized, summarized |
| `storage_path` | where the canonical copy lives |

Without this metadata, AI evidence quickly becomes anecdotal rather than defensible.

## 5. Collection priorities

During the first phase of an incident, prioritize preservation of:

1. session identifiers,
2. prompt and completion references or hashes,
3. tool invocations with parameters,
4. approval and policy decision events,
5. browser or CLI timestamps,
6. git refs, changed files, artifact IDs,
7. network and credential-rotation timeline.

### 5.1 Preserve both context and control flow

A transcript alone is not enough.

You need:

- what the agent saw,
- what it decided,
- which tool it tried to call,
- what the platform allowed or denied,
- what state changed afterwards.

This is the difference between a story and a useful investigation record.

## 6. Raw, canonical, and analyst copies

Maintain three layers where practical:

### 6.1 Raw capture

The nearest available original form.

Examples:

- exported audit log row,
- stored prompt blob,
- raw tool parameter JSON,
- original browser screenshot,
- exact CI artifact.

### 6.2 Canonical preserved copy

A normalized but fidelity-preserving copy used as the official evidence object.

Typical actions:

- convert timestamps to UTC,
- store UTF-8 consistently,
- record content hash,
- attach metadata,
- package with chain references.

### 6.3 Analyst-safe copy

A redacted or tokenized version for broader review.

Typical actions:

- mask secrets,
- replace personal data with placeholders,
- omit raw restricted exports,
- attach links back to canonical evidence.

Do not let the analyst-safe copy become the only remaining copy.

---

## 7. Normalization rules

Normalization should make evidence easier to compare without changing meaning.

Recommended steps:

- convert timestamps to UTC ISO-8601,
- preserve original time zone separately if relevant,
- normalize line endings and text encoding,
- extract structured fields from JSON logs,
- record invisible or control characters when they matter,
- keep original ordering of multi-step tool chains,
- separate content from analyst notes.

### 7.1 Prompt-specific normalization

For prompts and retrieved content:

- preserve raw original text in canonical storage,
- record whether the content came from user input, retrieval, browser DOM, email, ticket, or MCP tool,
- note any hidden-text stripping or rendering changes in the derived copy,
- hash the raw content before further transformation.

This matters because some attacks depend on hidden or transformed context.

---

## 8. Redaction and privacy handling

Prompt traces often contain the same sensitive data classes as tickets and logs.

Default rules:

- redact secrets before broad analyst distribution,
- mask personal data unless the investigation truly needs raw values,
- keep raw restricted evidence in tighter-access storage,
- track who accessed raw evidence,
- apply the same classification to transcripts as to the sensitive data they contain.

### 8.1 Redact carefully

Good redaction preserves investigation value.

| Data element | Better practice |
|---|---|
| API key or token | replace with token type and suffix only |
| Email address | mask local part unless identity is central to the incident |
| Support export rows | preserve small redacted subset plus secure link to raw artifact |
| Browser screenshots | blur or crop unrelated personal data |
| Chat transcript | split operationally relevant excerpts from raw full transcript |

For broader data-handling rules, align with `data-classification-and-handling.md` and `gdpr-security-ops.md`.

## 9. Safe replay and analysis

One of the biggest mistakes in AI incident handling is replaying dangerous evidence directly.

Never replay raw evidence against live systems by default.

### 9.1 Safe replay rules

- use an isolated sandbox or offline harness,
- disable network egress unless specifically needed,
- replace live credentials with stubs,
- stub destructive tools,
- mark replay output as **derived evidence**, not original evidence,
- preserve the exact replay environment version.

### 9.2 When replay is justified

Replay is useful when you need to confirm:

- whether a prompt or retrieved artifact reliably triggers a tool request,
- whether a policy rule correctly blocks the sequence,
- whether the issue survives after remediation.

But replay should help validation, not create a second incident.

## 10. Chain of custody

Even in internal investigations, chain of custody still matters.

Track:

- who collected the item,
- when it was collected,
- where it was stored,
- who accessed or transformed it,
- what derived versions were created,
- whether any part was redacted, summarized, or re-encoded.

### 10.1 Minimal chain log fields

| Field | Purpose |
|---|---|
| `action` | collected, hashed, redacted, exported, viewed, archived |
| `performed_by` | person or system performing the step |
| `performed_at_utc` | timestamp |
| `from_path` | prior storage location |
| `to_path` | new storage location |
| `notes` | why the action occurred |

If analysts pass evidence around in chat attachments with no log, chain quality is already degraded.

---

## 11. Storage model

Use storage tiers matched to sensitivity.

| Tier | Use | Example contents |
|---|---|---|
| Quarantine raw store | highest-sensitivity canonical evidence | raw prompts, raw transcripts, raw tool outputs, screenshots |
| Working evidence store | normalized and indexed evidence | parsed logs, metadata tables, timeline views |
| Analyst share | redacted evidence for responders and reviewers | masked excerpts, summary timelines, safe screenshots |

Expected controls:

- immutable or append-only behavior for canonical evidence where practical,
- strong access control,
- access logging,
- explicit retention and deletion rules,
- clear export approval for regulated data.

---

## 12. Common evidence mistakes

| Mistake | Why it hurts |
|---|---|
| Keeping only screenshots of a session | loses searchable and replayable structure |
| Deleting prompt traces during containment | destroys root-cause evidence |
| Mixing analyst opinions into raw evidence | reduces integrity and clarity |
| Sharing raw transcripts broadly | creates privacy and confidentiality spillover |
| Replaying evidence against live tools | may trigger another incident |
| Saving redacted summaries without the canonical parent | makes later validation impossible |
| Ignoring approval logs | loses the human decision trail |

---

## 13. First 15 minutes of evidence handling

1. Freeze the workflow without deleting traces.
2. Collect session IDs, timestamps, and control-plane logs.
3. Preserve tool-call records, approvals, and artifact references.
4. Move raw evidence into controlled storage.
5. Hash and register each major evidence object.
6. Generate analyst-safe copies only after canonical preservation.
7. Record any missing telemetry as an investigation gap immediately.

This sequence prevents most self-inflicted evidence loss.

---

## 14. Review output format

Use this summary structure for each major evidence object:

```text
Evidence: tool invocation sequence
Session: sess-2026-04-18-014
Trust label: Trusted telemetry
Classification: Confidential
Canonical storage: evidence/IR-2026-0418/tool-sequence.json
Observed issue: agent attempted external API call after reading untrusted browser content
Derived copies: redacted sequence for analyst review, timeline extract for postmortem
Next action: verify whether policy downgrade should have prevented the call
```

This keeps evidence review concise without losing custody and classification context.

## 15. Minimum checklist

| Check | Expected |
|---|---|
| Session IDs, tool calls, approvals, and artifact refs are preserved | Yes |
| Raw evidence is stored before redaction or summarization | Yes |
| Each evidence object has hash, owner, trust label, and classification | Yes |
| Derived evidence links back to canonical parent evidence | Yes |
| Replay is sandboxed and never live by default | Yes |
| Prompt traces follow privacy and confidentiality handling rules | Yes |
| Access to raw evidence is logged and restricted | Yes |
| Missing telemetry is recorded as an explicit gap | Yes |
