# AI Coding CLI Hardening (Claude Code / Codex / Gemini CLI)

> Last reviewed: 2026-04-06 | Next review: 2026-10-06 | Priority: Essential | Audit Level: 2-3 | Automation: Partial (policy lint + CI guardrails automatable; threat model/manual approvals required)

This guide adds **operational hardening controls** for local and CI usage of AI coding CLIs (Claude Code, Codex CLI, Gemini CLI, and similar tools).

Use this when AI agents can read files, run commands, call external tools, or create commits.

---

## 1. Security Objectives

1. Prevent code/data exfiltration from local workstations and CI runners.
2. Prevent unauthorized state-changing actions (delete, deploy, publish, force-push).
3. Make every sensitive AI action auditable and attributable.
4. Keep workflows usable: secure-by-default with explicit, temporary elevation.

---

## 2. Threat Model for AI Coding CLI

### Primary assets

- Source code and design docs
- Secrets (`.env`, API keys, cloud credentials)
- Git history and release integrity
- CI tokens and cloud deployment credentials

### Common attack paths

- Prompt injection via copied issue text, README, web page, or PR comment
- Malicious/over-privileged MCP tools
- Dependency/supply-chain compromise in helper tools
- Unsafe command execution generated by model
- Accidental data disclosure in model context or logs

Related controls: `llm-agent-security.md`, `mcp-security.md`, `supply-chain-security.md`.

## 3. Baseline Profile (Default Deny)

Apply this profile to all AI coding CLIs by default:

- **Filesystem:** read-only unless a task explicitly needs writes.
- **Network:** disabled by default; allowlist only required domains.
- **Command execution:** disabled by default; allowlist command families.
- **Git:** no push, no tag, no release from agent by default.
- **Secrets:** never injected into model context; available only to runtime tool layer.

### Permission tiers

- **Tier 0 (Read-only):** read files, static analysis, test planning.
- **Tier 1 (Local write):** edit files in workspace, run formatting/lint/test.
- **Tier 2 (External write):** network calls, package install, artifact upload.
- **Tier 3 (High impact):** deploy, delete resources, force-push, permission changes.

Rules:

- Start at Tier 0.
- Tier 1+ requires explicit user confirmation and task justification.
- Tier 2+ requires time-bounded elevation and strong audit logging.
- Tier 3 requires human approval out-of-band (never autonomous in production).

## 4. Policy-as-Code Template

Store policy in-repo and enforce it in CI.

```yaml
# .ai/agent-policy.yaml
version: 1

default:
  tier: 0
  network: deny
  filesystem: read_only
  git:
    allow_commit: true
    allow_push: false

allowlists:
  commands:
    - "git status"
    - "git diff"
    - "npm test"
    - "pytest"
  domains:
    - "api.github.com"

approvals:
  require_for:
    - "rm"
    - "git push"
    - "docker push"
    - "kubectl apply"
  ttl_minutes: 15

logging:
  include:
    - timestamp
    - user_id
    - session_id
    - model
    - tool_name
    - decision
  redact:
    - "*token*"
    - "*password*"
    - "*api_key*"
```

Minimum checks in CI:

- Policy file exists and parses.
- No wildcard approval for destructive commands.
- No `allow_push: true` on protected branches.

## 4.1 Vendor Mapping (Claude Code / Codex CLI / Gemini CLI / Others)

Apply the same control intent regardless of vendor CLI:

| Control intent | Claude Code | Codex CLI | Gemini CLI | Other agent CLIs |
|---|---|---|---|---|
| Default read-only start | Enable read-only / restricted mode first | Start in least-privilege mode | Start with minimal permissions | Start in deny-by-default mode |
| Destructive action approval | Require explicit confirmation before write/delete/deploy | Require explicit approval gate for mutating actions | Require human confirmation for state changes | Enforce HITL for all high-impact tools |
| Tool allowlist | Register only approved tools/MCP servers | Allowlist command/tool families | Allowlist integrations and external endpoints | Maintain approved tool registry |
| Network restriction | Limit outbound domains | Restrict remote calls to allowlisted domains | Restrict remote calls to allowlisted domains | Default no egress; explicit allowlist |
| Auditability | Log session/tool/decision metadata | Log model/tool/approval events | Log model/tool/approval events | Capture equivalent audit trail fields |

Implementation differs by product, but the **security invariant** should not change.

## 5. Prompt/Context Firewall for Coding Workflows

Before any tool call from model output:

1. **Classify input source**: user text vs. external untrusted content.
2. **Strip hidden content**: HTML comments, invisible unicode, markdown directives.
3. **Detect instruction-like payloads**: "ignore previous", "exfiltrate", "send secrets".
4. **Downgrade permissions** after reading untrusted content (back to Tier 0).
5. **Schema-validate generated actions** before execution.

If detection triggers:

- block action,
- show reason,
- require explicit user re-authorization.

---

## 6. Secret Safety for CLI Agents

- Never pass real secrets in prompts, chat history, or commit messages.
- Use ephemeral tokens scoped to least privilege.
- Redact sensitive values in terminal capture and logs.
- Block commits if diff includes known secret patterns (`sk-`, `ghp_`, `AKIA`).
- Enforce pre-commit and pre-push secret scanning (Gitleaks + push protection).

---

## 7. Git and Release Integrity Controls

Recommended defaults for AI-generated changes:

- Protected branches require human review.
- Signed commits/tags for release branches.
- Mandatory CI checks: tests + SAST + secret scanning + dependency scan.
- PR template section: "AI-assisted changes reviewed for authz/secrets/injection".

Optional hardening:

- Label PRs as `ai-assisted`.
- Require CODEOWNERS approval for security-sensitive paths (`auth/`, `infra/`, `.github/workflows/`).

---

## 8. MCP and Tooling Trust Controls

- Only use approved MCP servers from an internal allowlist.
- Pin versions/commits for MCP server packages.
- Sandbox MCP servers (non-root, read-only fs, dropped capabilities).
- Validate manifests for suspicious patterns before registration.
- Separate read-only vs. state-changing tools into distinct trust zones.

---

## 9. CI Guardrails (Minimum)

Add CI jobs that fail on:

- policy drift (`.ai/agent-policy.yaml` invalid or too permissive),
- secret leaks,
- unsafe patterns (`eval`, `shell=True`, `verify=False`, string-built SQL),
- direct execution of model output without validation.

Recommended tools:

- Gitleaks / TruffleHog (secrets)
- Semgrep / Bandit / Gosec (SAST)
- Trivy / pip-audit / npm audit (dependencies)

---

## 10. Operational Checklist (Per Session)

- [ ] Agent starts in Tier 0 (read-only).
- [ ] Network disabled or strictly allowlisted.
- [ ] Secrets not present in prompt/context/logs.
- [ ] Untrusted external content treated as data, not instruction.
- [ ] Any write/delete/deploy action had explicit approval.
- [ ] Session logs include actor, tool, decision, timestamp, model.
- [ ] Before push: secret scan + dangerous pattern scan + tests pass.

## 11. Maturity Roadmap

### Level A - Solo developer

- Local pre-commit secret scanning
- Tier 0 default profile
- Manual review before push

### Level B - Startup team

- Shared policy-as-code
- CI enforcement and protected branches
- MCP allowlist and signed releases

### Level C - Enterprise

- Central policy distribution
- Fine-grained per-repo/per-path controls
- SIEM integration and periodic red-team exercises for agent workflows

---

## 12. Minimal Rollout Plan (14 Days)

### Days 1-3
- Define Tier 0/Tier 1 controls and destructive action approval policy.
- Block pushes from agent sessions by default on protected branches.

### Days 4-7
- Add policy lint in CI and enforce secret scanning on pre-commit + pre-push.
- Add prompt/context firewall checks for copied external content.

### Days 8-14
- Add MCP/tool allowlist process and approval ownership.
- Run one tabletop simulation of prompt-injection-to-tool-execution scenario.
