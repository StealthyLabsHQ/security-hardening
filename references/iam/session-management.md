# Session Management

> Last reviewed: 2026-04-14 | Next review: 2026-10-14 | Priority: Essential | Audit Level: 2-3 | Automation: Partial (cookie checks, timeout tests, and revocation flows automatable; risk-based re-auth and recovery design manual)

Sessions are often treated as "solved" once login works. They are not. A strong authentication flow can still be broken by weak session rotation, weak invalidation, or weak logout semantics.

Use this guide for cookie-based web sessions, server-stored sessions, refresh-token flows, and "log out other devices" features.

---

## 1. Core Rules

- Session identifiers must be unpredictable and generated by a CSPRNG.
- Rotate the session identifier after login and after privilege elevation.
- Invalidate sessions server-side on logout, password change, account recovery, or suspicious activity.
- Use `Secure`, `HttpOnly`, and appropriate `SameSite` cookie attributes.
- Apply idle timeout and absolute lifetime.
- Keep a server-side source of truth for revocation, session versioning, or current session list.

---

## 2. Rotation Events

Rotate the session or equivalent token when:

- the user authenticates,
- MFA step-up succeeds,
- privilege changes from standard to admin,
- password is changed,
- account recovery is completed,
- a suspicious concurrent session is detected and you keep the user signed in.

If the session ID stays the same across login, you are vulnerable to **session fixation**.

---

## 3. Cookie Baseline

```http
Set-Cookie: session=...; Path=/; Secure; HttpOnly; SameSite=Lax
```

Recommendations:

- `SameSite=Lax` for normal first-party web apps.
- `SameSite=Strict` for highly sensitive apps that can tolerate stricter navigation behavior.
- `SameSite=None; Secure` only when cross-site usage is intentionally required.
- Narrow `Domain` and `Path` where possible.

Do not store long-lived bearer secrets in `localStorage`.

## 4. Server-Side Session Pattern

```python
def login(user_id: str, response):
    session_id = secrets.token_urlsafe(32)
    store_session(session_id, user_id=user_id, session_version=current_version(user_id))
    response.set_cookie(
        "session",
        session_id,
        secure=True,
        httponly=True,
        samesite="Lax",
    )

def logout(request, response):
    invalidate_session(request.cookies["session"])
    response.delete_cookie("session")
```

**Important:** deleting the cookie alone is not logout. The server must revoke the session record too.

---

## 5. JWT / Refresh Token Pattern

If you use access tokens:

- keep access tokens short-lived,
- store refresh tokens server-side or make them revocable,
- rotate refresh tokens on every use,
- detect replay of an already-rotated refresh token,
- keep a user/session version to revoke old tokens after account events.

JWTs are not "self-revoking". If you cannot revoke them, your logout and recovery story is weak.

---

## 6. Concurrent Sessions

Decide the policy explicitly:

| Policy | Best for |
|--------|----------|
| Unlimited sessions | low-risk consumer apps with visible session management |
| Soft cap + user visibility | most SaaS products |
| Single active session | admin consoles, finance, or highly sensitive internal tools |

Minimum controls:

- list active sessions/devices,
- show last seen time and IP/region hint,
- let the user revoke other sessions,
- alert on unusual concurrent geography or device patterns.

---

## 7. Invalidation Events

Revoke all or selected sessions when:

- password changes,
- MFA factor is removed or reset,
- account recovery succeeds,
- role/permission changes,
- compromise is suspected,
- admin manually disables the user.

For sensitive admin actions, require re-authentication or step-up even with an active session.

---

## 8. Timeouts

Use both:

- **idle timeout**: expire after inactivity,
- **absolute timeout**: expire after a maximum lifetime regardless of activity.

Example starting points:

| App type | Idle | Absolute |
|----------|------|----------|
| Typical SaaS | 15-30 min | 8-24 h |
| Admin console | 10-15 min | 4-8 h |
| Finance / highly sensitive | 5-15 min | 1-4 h |

Tune based on risk and usability, but document the choice.

---

## 9. Session Fixation Test Ideas

- Login should issue a new session ID, not reuse the pre-login one.
- Privilege elevation should rotate the session again.
- Logout should invalidate the old session server-side.
- Password change should invalidate existing sessions.
- "Log out other devices" should revoke every session except the current one.

Related tests belong in `security-testing-examples.md`.

---

## 10. Common Failure Modes

- Cookie deleted, but server session still valid.
- Password changed, but old sessions keep working.
- MFA added, but pre-MFA session remains unchanged.
- Admin role granted, but no re-authentication or session rotation.
- Access token expires, but refresh token lives forever with no revocation.
- Session list exists, but users cannot revoke other sessions.

---

## 11. Checklist

| Check | Expected |
|-------|----------|
| Session rotates after login and privilege changes | Yes |
| Logout revokes server-side session state | Yes |
| Password change invalidates existing sessions | Yes |
| Idle and absolute timeouts are defined | Yes |
| Cookie uses `Secure`, `HttpOnly`, correct `SameSite` | Yes |
| User can view and revoke active sessions | Yes |
| Sensitive actions require re-auth or step-up | Yes |
