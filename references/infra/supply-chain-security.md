## 1. SLSA Framework (Supply chain Levels for Software Artifacts)

SLSA (pronounced "salsa") is a security framework from Google/OpenSSF that defines levels of supply chain integrity. Each level adds verifiable guarantees about how software was built.

| Level | Requirements | Protects against |
|-------|-------------|-----------------|
| **SLSA 0** | No guarantees | - |
| **SLSA 1** | Build process is scripted/automated; provenance exists | Accidental errors |
| **SLSA 2** | Provenance signed by CI service; version-controlled build | Tampering after build |
| **SLSA 3** | Provenance generated by hardened CI; hermetic builds | Compromised build system |

**SLSA 2 is the realistic target for most teams.** SLSA 3 requires hermetic build isolation (no network access during build, fully reproducible).

**Generate SLSA provenance with GitHub Actions (slsa-github-generator):**

```yaml
# .github/workflows/release.yml
jobs:
  build:
    outputs:
      digests: ${{ steps.hash.outputs.digests }}
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build artifact
        run: |
          make release
          sha256sum artifacts/* > checksums.txt
      - name: Generate artifact hash
        id: hash
        run: |
          echo "digests=$(cat checksums.txt | base64 -w0)" >> "$GITHUB_OUTPUT"

  provenance:
    needs: [build]
    permissions:
      actions: read
      id-token: write
      contents: write
    uses: slsa-framework/slsa-github-generator/.github/workflows/generator_generic_slsa3.yml@v2.0.0
    with:
      base64-subjects: "${{ needs.build.outputs.digests }}"
      upload-assets: true
```

**Verify SLSA provenance before using an artifact:**

```bash
# Install slsa-verifier
go install github.com/slsa-framework/slsa-verifier/v2/cli/slsa-verifier@latest

# Verify downloaded artifact
slsa-verifier verify-artifact artifact.tar.gz \
  --provenance-path artifact.tar.gz.intoto.jsonl \
  --source-uri github.com/myorg/myrepo \
  --source-tag v1.2.3
```

## 2. SBOM (Software Bill of Materials)

An SBOM is a machine-readable inventory of all components in your software. During Log4Shell, the first question was "do I have this library anywhere?" - teams with SBOMs answered in minutes; others took weeks.

**Formats:**
- **SPDX** - Linux Foundation standard, widely supported
- **CycloneDX** - OWASP standard, richer vulnerability data, preferred for security tooling

**Generate SBOM with Syft:**

```bash
# Install
brew install syft  # or: curl -sSfL https://raw.githubusercontent.com/anchore/syft/main/install.sh | sh

# Generate SBOM for a directory (your repo)
syft dir:. -o spdx-json > sbom.spdx.json
syft dir:. -o cyclonedx-json > sbom.cyclonedx.json

# Generate SBOM for a Docker image
syft myregistry/myapp:v1.0.0 -o cyclonedx-json > image-sbom.json

# Generate SBOM for a specific package ecosystem
syft dir:. --scope all-layers -o table  # human-readable summary
```

**Generate SBOM with Trivy:**

```bash
# SBOM from filesystem
trivy fs --format cyclonedx --output sbom.json .

# SBOM from Docker image
trivy image --format spdx-json --output image-sbom.json myapp:latest
```

**CI/CD integration - generate and attach SBOM to every release:**

```yaml
# .github/workflows/security.yml
- name: Generate SBOM
  uses: anchore/sbom-action@v0
  with:
    path: .
    format: cyclonedx-json
    artifact-name: sbom.cyclonedx.json
    upload-artifact: true

- name: Scan SBOM for vulnerabilities
  run: |
    trivy sbom sbom.cyclonedx.json --exit-code 1 --severity CRITICAL,HIGH
```

**Check if a specific CVE affects your SBOM:**

```bash
# After Log4Shell dropped - check SBOM immediately
grype sbom:sbom.cyclonedx.json | grep -i "log4j\|CVE-2021-44228"
```

## 3. Dependency Confusion Attack

**How it works:**

1. Your organization uses an internal package `mycompany-utils` at version `1.0.0`, installed from a private registry.
2. An attacker discovers the internal package name (from a job posting, public code, error message).
3. Attacker publishes `mycompany-utils` version `9.9.9` to the **public** npm/PyPI registry.
4. If your package manager checks public registries first (or at the same time as private), it downloads version `9.9.9` over your internal `1.0.0`.
5. The attacker's package runs malicious code during install (`postinstall` script).

**Real-world impact:** Alex Birsan demonstrated this in 2021, gaining RCE at Apple, Microsoft, PayPal, Netflix, and 30+ other companies.

**Mitigations for npm:**

```bash
# Use scoped packages - attackers cannot claim @mycompany/ namespace on public npm
# without owning that scope
npm install @mycompany/utils   # safe - scoped

# Pin registry per scope in .npmrc
echo "@mycompany:registry=https://npm.mycompany.internal" >> .npmrc

# Or use a private registry proxy (Artifactory, AWS CodeArtifact)
# that blocks public packages if a private one exists with the same name
npm config set registry https://mycompany.jfrog.io/artifactory/api/npm/npm/
```

**.npmrc configuration:**

```ini
# .npmrc
@mycompany:registry=https://npm.mycompany.internal/
//npm.mycompany.internal/:_authToken=${NPM_INTERNAL_TOKEN}

# Block public fallback for internal scopes
@mycompany:always-auth=true
```

**Mitigations for pip:**

```bash
# Use --index-url to pin to private registry (does NOT fall back to PyPI)
pip install mycompany-utils --index-url https://pypi.mycompany.internal/simple/

# Wrong: --extra-index-url STILL checks PyPI and takes the highest version
# pip install mycompany-utils --extra-index-url https://pypi.mycompany.internal/simple/

# In pip.conf / pyproject.toml - restrict to private only
[global]
index-url = https://pypi.mycompany.internal/simple/
```

**Additional controls:**

```bash
# Pre-register your internal package names on public PyPI/npm as empty placeholders
# This prevents attackers from squatting the name

# Always use lockfiles - pin exact versions
npm ci           # uses package-lock.json exactly, never resolves higher versions
pip install -r requirements.txt  # with pinned versions and hashes

# Verify package hashes in pip
pip install --require-hashes -r requirements.txt
# requirements.txt with hashes:
# mypackage==1.2.3 \
#     --hash=sha256:abc123...
```

## 4. Artifact Signing with Cosign / Sigstore

Signing artifacts (Docker images, binaries, git commits) lets consumers verify that what they received was produced by your CI pipeline and was not tampered with.

**Sigstore / Cosign keyless signing (preferred - uses OIDC identity from CI):**

```bash
# Install cosign
brew install cosign

# Sign a Docker image (keyless - uses GitHub Actions OIDC token)
# In GitHub Actions:
- name: Sign image
  env:
    COSIGN_EXPERIMENTAL: "true"
  run: |
    cosign sign --yes \
      myregistry/myapp@${{ steps.build.outputs.digest }}
```

**Full GitHub Actions workflow with build, push, and sign:**

```yaml
- name: Build and push
  id: build
  uses: docker/build-push-action@v5
  with:
    push: true
    tags: myregistry/myapp:${{ github.sha }}

- name: Sign image
  uses: sigstore/cosign-installer@v3
- run: |
    cosign sign --yes \
      myregistry/myapp@${{ steps.build.outputs.digest }}
  env:
    COSIGN_EXPERIMENTAL: "true"
```

**Verify a signed image before deployment:**

```bash
cosign verify \
  --certificate-identity-regexp="https://github.com/myorg/myrepo" \
  --certificate-oidc-issuer="https://token.actions.githubusercontent.com" \
  myregistry/myapp@sha256:abc123...
```

**Sign git commits with gitsign (Sigstore-backed):**

```bash
# Install gitsign
go install github.com/sigstore/gitsign@latest

# Configure git to use gitsign
git config --global gpg.x509.program gitsign
git config --global gpg.format x509
git config --global commit.gpgsign true

# Commits are now signed with your OIDC identity (GitHub, Google, etc.)
git commit -m "feat: add feature"

# Verify
git log --show-signature -1
```

## 5. CI/CD Pipeline Security

**Pin GitHub Actions to commit SHAs, not version tags:**

```yaml
# Vulnerable - attacker can push to v3 tag and inject code
- uses: actions/checkout@v4
- uses: some-action/do-thing@v2

# Safe - pinned to immutable commit hash
- uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683  # v4.2.2
- uses: some-action/do-thing@a1b2c3d4e5f6...  # v2.1.0
```

Use `pin-github-action` or `Dependabot` to keep pinned hashes updated:

```bash
# Pin all actions in a workflow file
npx pin-github-actions .github/workflows/security.yml
```

**Minimal permissions per workflow and job:**

```yaml
# Top-level: deny all by default
permissions: read-all

jobs:
  build:
    permissions:
      contents: read       # only what this job needs
      packages: write      # to push to GHCR

  deploy:
    permissions:
      id-token: write      # for OIDC cloud authentication
      contents: read
```

**Use OIDC instead of long-lived static keys for cloud auth:**

```yaml
# Instead of storing AWS_ACCESS_KEY_ID in secrets, use OIDC
- name: Configure AWS credentials
  uses: aws-actions/configure-aws-credentials@v4
  with:
    role-to-assume: arn:aws:iam::123456789:role/github-actions-role
    aws-region: us-east-1
    # No static key needed - uses short-lived OIDC token
```

**Artifact integrity - checksum and verify:**

```yaml
- name: Build binary
  run: make build

- name: Compute checksum
  run: sha256sum dist/myapp > dist/myapp.sha256

- name: Upload with checksum
  uses: actions/upload-artifact@v4
  with:
    name: release-artifacts
    path: |
      dist/myapp
      dist/myapp.sha256

# In the deployment job - verify before use
- name: Verify checksum
  run: sha256sum -c dist/myapp.sha256
```

## Supply Chain Security Checklist

| Check | Expected |
|-------|----------|
| Internal packages use scoped names (`@mycompany/`) or private registry with no public fallback | Yes |
| Lockfiles committed and used in CI (`npm ci`, `pip install --require-hashes`) | Yes |
| SBOM generated and attached to every release | Yes |
| SBOM scanned for CVEs in CI pipeline | Yes |
| Docker images signed with Cosign | Yes |
| GitHub Actions pinned to commit SHAs | Yes |
| Workflows use minimal permissions (deny-all at top, grant per job) | Yes |
| Cloud auth uses OIDC, not stored static keys | Yes |
| SLSA provenance generated for releases | Level 1+ |
| OpenSSF Scorecard run on main repositories | Yes |
| Dependency updates automated (Dependabot or Renovate) | Yes |

## Academic grounding

### Open-source package attacks mostly exploit trust and automation

Ladisa et al. (2023) mapped 107 attack vectors across open-source supply chains to dozens of confirmed incidents and showed that many high-impact compromises do not require a novel exploit. They succeed because automation trusts registries, maintainer identities, release scripts, and transitive resolution too broadly.

Use that finding to tighten practical controls:

- prefer exact version and hash pinning over loose semver ranges,
- block public fallback for internal package names and scopes,
- treat install-time scripts, obfuscated packages, and network activity during dependency install as high-signal review events,
- separate maintainer identity hardening from artifact integrity hardening because both are needed.

### Additional review questions

When reviewing a package or release pipeline, explicitly ask:

- can a public registry artifact outrank or impersonate an internal package,
- can a compromised maintainer or CI job publish without a second integrity signal,
- can an install hook run code before the package is reviewed or built,
- can the build consume unpinned remote content or mutable tags.

These checks align well with the incident patterns Ladisa et al. cataloged and help keep the review focused on the real sources of supply-chain risk rather than only CVE counts.
